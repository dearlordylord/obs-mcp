# OBS MCP competitor discovery — 2026-09-13

This is a bounded follow-up to [`obs-competitor-index.json`](obs-competitor-index.json), whose previous snapshot was 2026-06-13. I searched public GitHub repositories and first-party package registries for OBS Studio MCP servers, then read the pinned repository metadata and source declarations. I did not run competitor code. Counts below come from checked-in registries/decorators where available; a README-only count is marked as an advertisement and is not treated as proof.

The current local source has 159 MCP tool registrations across the protocol categories, resources, bounded events, and HTTP transport ([`src/mcp/tools/index.ts`](../src/mcp/tools/index.ts), [`README.md`](../README.md)). That registration count does not prove request coverage. A static request-name comparison is included below for the closest full-surface Rust competitor. The new competitors expose several higher-level product ideas that deserve separate prioritization: dry-run previews, one-call audio/health workflows, automatic OBS startup, a reproducible desktop package, Linux plugin lifecycle management, and a human web dashboard.

## JLFN request-set check

I compared the request names in JLFN's generated [`src/tools_table.rs`](https://github.com/JLFN/obs-mcp/blob/f9dccf0f8903b225615ba3b80a8a63287b92716a/src/tools_table.rs) with the local [`obs-websocket-surface-matrix.json`](obs-websocket-surface-matrix.json). The result is precise:

- JLFN has 157 table entries but 151 unique request names.
- The local matrix has 147 unique request names, and all 147 are present in JLFN's table.
- JLFN-only names are `GetSceneItemPrivateSettings`, `SetSceneItemPrivateSettings`, `GetSourcePrivateSettings`, and `SetSourcePrivateSettings`. They are absent from the current official 147-request snapshot ([obs-websocket commit `1ef34bf`](https://github.com/obsproject/obs-websocket/tree/1ef34bf48110c2a18184e50e41cd0b1a855e2147)); support in a different OBS build or fork is unverified. Do not add them from competitor evidence alone.
- Six of JLFN's extra table entries are convenience aliases, not new protocol requests: three wrappers for `GetVersion` (`obs-get-status`, `obs-get-version`, `obs-test-connection`), two for `TriggerStudioModeTransition` (`obs-trigger-studio-transition`, `obs-trigger-transition`), and four for `GetCurrentSceneTransition` (`obs-get-current-transition`, `obs-get-transition-duration`, `obs-get-transition-kind`, `obs-get-transition-settings`). The latter group contributes three extras and the first two groups contribute three, accounting for 157 entries versus 151 unique names.
- `Sleep` is in the official set. Local deliberately exposes it only as a schema-limited batch item ([`README.md`](../README.md)); JLFN's standalone `obs-sleep` is a semantic/policy difference, not a missing official request wrapper.

Therefore this comparison finds no current official request-name deficit. It does identify four JLFN-only private-settings names for a future upstream-protocol watch, plus a useful aliasing pattern for user-facing convenience tools.

## What to carry into the gap plan

The discoveries do not justify expanding the core typed OBS protocol surface merely to match counts. The local source already covers the same broad categories and adds bounded event confirmation, capability-gated resources, screenshot path policy, request batches, and toolset filtering ([`README.md`](../README.md)). The evidence supports these focused follow-ups:

1. Add a dry-run/preview contract for selected mutating workflows. Aaron's server applies it consistently, while local tool annotations currently communicate behavior but do not provide a side-effect-free preview payload.
2. Add higher-level, opt-in workflow tools after protocol correctness is stable: AV-health diagnosis and audio-chain setup are the strongest repeated product signals from xDarkzx and Aaron. Keep them separate from raw tool parity and validate filter/source capabilities at runtime.
3. Evaluate closed-OBS startup as a lifecycle feature. JLFN's `OBS_START_COMMAND` is concrete, but it requires a deliberate shell-command policy and platform-specific behavior; treat it as a design item rather than copying the interface.
4. Add a reproducible desktop/MCPB packaging check if desktop distribution is a target. Tom-R-Main's packaging is the clearest new distribution signal; the local npm package currently documents npx and HTTP/stdio deployment but does not ship an MCPB artifact ([`package.json`](../package.json)).
5. Keep Linux device/plugin/dashboard integration as an adjacent roadmap lane. ITchrisDEB demonstrates substantial user value, but its Linux-only services and plugin installers materially widen security and maintenance scope.

These are comparative signals only. None of the repositories were executed, and no live OBS instance was used for parity validation. Counts and advertised capabilities should be rechecked with each project's runtime `tools/list` and package release metadata before implementation commitments.

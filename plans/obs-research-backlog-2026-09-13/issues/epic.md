## Implementation Decisions

- Retain the existing TypeScript/Effect architecture and documented toolset/capability policy. Adopt independent design strengths through observable product contracts.
- Use one parent tracker with five first-milestone implementation children, five later workflow/discovery children, and three bounded decision/audit children.
- Keep the full finding-to-disposition map in this parent and a repository mirror. Every actionable finding has a linked destination, preserve-existing evidence, or explicit rejection rationale.
- Historical comparative evidence remains pinned; new baseline and release evidence name their actual source and artifact.
- Ready-for-agent indicates the spec is triaged, not that dependency-blocked or later-milestone work may start early.
- Existing issue #2 is a reconciliation target, not a duplicate implementation task: verify its stated subscription and retention acceptance before closing or narrowing it.
- Parent completion requires linked implementation children to meet acceptance and decision children to resolve every direction with explicit follow-ups or rejection. Unresolved later work keeps the parent open.

## Testing Decisions

- Primary acceptance seam approved by the user: freshly installed package through MCP against controlled OBS, with focused existing protocol/HTTP tests where necessary and separate isolated real OBS/client visual verification before release.
- Test external results, resulting OBS state, errors, bounds and artifact identity; avoid coupling assertions to module layout or tool counts.
- Use the study's counterexamples as regression inputs after correcting known fixture-oracle limitations.
- Audit finding coverage, dependencies, acceptance evidence and actual release attribution before marking milestones or parent complete.

Tests assert externally observable behavior, actual OBS state, explicit errors and bounds; they must not mirror implementation structure. Prior art is the existing packed-package smoke, real fake-OBS socket harness, MCP handler/resource tests, HTTP lifecycle tests and opt-in real OBS integration. Reuse these boundaries.

## Out of Scope

Implementing production code during spec publication; promising all investigated product directions; native/framework rewrites; arbitrary execution; unbounded data collection; publishing npm packages without release authorization.

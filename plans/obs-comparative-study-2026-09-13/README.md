# OBS MCP comparative study — 2026-09-13

**The immediate opportunity is better fidelity and better user workflows. Royshil has not advanced since the previous review, and its larger-looking interface does not establish a working feature lead. Our implementation has concrete settings and selector limitations; newer competitors also provide useful audio, health, visual, and onboarding workflows.** This study evaluates those claims through pinned source, attributable packages, and actual MCP subprocesses against a shared deterministic OBS fixture.

Local baseline: [`@firfi/obs-mcp@0.3.3`, commit `587e356b00d9269dcd124969ee36aad9635f2db8`](https://github.com/dearlordylord/obs-mcp/tree/587e356b00d9269dcd124969ee36aad9635f2db8). Research only: no production implementation, publishing, real OBS operation, or stream was performed.

## How this follows the crap4ts research

The model is the sibling project's [alternative-implementations study](../../../crap4ts/research/2026-08-25-alternative-implementations.md): define the reference job first, freeze viability gates before scoring, inspect pinned implementations, execute a shared external fixture, separate architecture quality from complete-job eligibility, examine Pareto tradeoffs and weight sensitivity, and recommend a combination of independent strengths. The [methodology](methodology.md) records the OBS-specific gates, A–F rating anchors, weights, evidence rules, and an explicit late-census amendment. Ratings were assigned by reviewers; the local implementation received independent scoring.

The direct field contains 18 external implementations plus local. Additional event-history analysis accompanies the direct reviews; three live-production applications/wrappers have a separate lane. The [census](study/census.md) and [publication ledger](study/releases.json) record commits, package identities, versions, licenses, discovery limits, and exclusions. This is a comprehensive bounded study of the discovered field, not a claim that every OBS-related repository on the internet has been found.

## Results and how to read them

The generated [comparison and sensitivity tables](comparison-table.md) are the authoritative consolidated scores; [rankings.json](results/rankings.json) retains all ratings, gates, confidence, and evidence references. Scores describe architecture under an explicit rubric. They are not percentages of OBS features implemented or probabilities of reliability.

Gates are entry, protocol/identity, truthful state/results, bounded failures, complete reference workflow, and honest MCP contract. **P** is observed pass, **p** partial, **F** demonstrated failure or absent required capability, and **NT** an environment/evidence blocker. Any partial, failure, or untested gate prevents an unqualified complete-job winner. A platform blocker does not become an invented runtime defect.

Our local candidate scored **80/100** independently, with G1–G5 passing and G6 partial because repository architecture documentation still calls shipped capabilities deferred. It completed the finite inspection → scene/audio mutation → recording → screenshot job and returned truthful injected failures. This result used all toolsets and a configured one-second timeout; it is not a default-configuration or performance claim. The tested fresh package's SHA1 and SHA512 match the owning npm registry's published artifact integrity. [Local review](candidates/local.md), [publication evidence](results/local-publication.json).

**Architecture leader: DCC MCP OBS, 85/100. Local and Giancarlo pass all five execution gates, with MCP/documentation qualifications. No implementation passes every gate without qualification.** DCC's source and own tests provide the strongest protocol/state design evidence, but its native-plugin/MCP path is untested in this environment. Local scores 80 with a documentation partial; Giancarlo scores 66.25 and completes the same finite job with MCP-contract qualifications. These are materially different limitations from a failed runtime or an unavailable native environment. ITchris, JLFN, Tom, and xDark tie at 70 under the fixed weights, with different failure and scope boundaries.

DCC ranks first and local second under fixed, equal, and correctness-heavy weights. The four-way 70 tie separates under alternative weights: equal weights favor JLFN/Tom's balance, while correctness-heavy weights favor ITchris/xDark's protocol and workflow fitness. The raw-score **Pareto frontier** is DCC, ITchris, xDark, and Giancarlo: none is at least as strong as another across every scored dimension. DCC's ratings dominate local's because its protocol/state rating is higher and the remaining ratings equal; that does not replace local's stronger external execution evidence. The frontier ignores gate eligibility, and weight sensitivity cannot remove uncertainty in the underlying ratings. [Complete calculations](comparison-table.md).

## Where we are behind

These are demonstrated local limits, regardless of the ranking. Rejected unsupported arguments are not falsely successful writes, but users still cannot complete those jobs through the current interface. [Detailed local source and runtime evidence](candidates/local.md).

## Recommended work, in order

1. **Close known fidelity gaps.** Expose current transition settings through the existing valid request; preserve nested filter/output JSON with an explicit read/write contract; add the three missing selectors. Verify round trips and exact outgoing request fields. Keep documented typed conveniences where useful, and make any raw/opaque settings path explicit. Do not implement Roy's nonexistent transition-settings request.
2. **Make protocol parity field-aware.** Compare descriptor/tool schemas with the pinned protocol, distinguish deliberate restrictions from omissions, and exercise representative nested plugin settings and UUID-only/canvas-specific targets. Preserve the current truthful validation and error behavior. Correct stale architecture documentation and descriptor-count language alongside this work.
3. **Complete the visual interface.** Return native MCP image content or an explicit image resource while retaining bounded payload policy. Define remote screenshot-save semantics instead of assuming the MCP host can validate OBS's filesystem. Test image content through an actual supported MCP client before claiming an improved visual agent loop.
4. **Prototype one valuable workflow over existing primitives.** AV-health diagnosis or an audio-cleanup preview has the strongest competitor signal. Define observed versus inferred health, prerequisites, dry-run output, partial failure, final readback, and event-confirmation limits before adding broad workflow families. Reuse the existing bounded event machinery.
5. **Improve distribution where it solves measured friction.** Evaluate MCPB and an explicit startup/connection diagnostic flow for target clients. Preserve artifact attribution and fresh-install smoke checks; source tests did not protect competitors from dependency-resolution or entrypoint failures.

DCC also deserves a focused architecture follow-up: compare its propagated deadlines, readback/postcondition checks, and explicit uncertain-outcome contract with our existing cancellation and non-retry behavior. Exact OBS PID/plugin-instance binding depends on its native extension and cannot be assumed available through ordinary obs-websocket. Verify the transferable design ideas before considering a native-plugin product direction.

Dashboards, live transcription, avatar/TTS streaming, device/plugin management, and OS setup remain distinct product choices. The [adjacent review](study/adjacent.md) explains their useful designs: Live Suite's domain-level tools and operator approval, MoltStream's status/chat/trace vocabulary, the Claude wrapper's backup/onboarding workflow, and specialist event-history diagnostics. BEA’s [creator workflows](candidates/bea.md) additionally model named computers, readiness checks, explicit confirmation, and restoration after multi-step changes; these are source-level designs, not verified hosted production behavior here. Their strengths can inform interfaces without importing their entire product scope.

## Evidence quality, reproduction, and limits

The [fixture](fixture/README.md) drives real candidate MCP stdio processes against a loopback OBS WebSocket v5 model with authentication, JSON/MsgPack support, deterministic state, selected capabilities, valid PNG data, synthetic secrets, and injected failures. The final common revision is **2026-09-13.5**. Candidate launch/tool adapters translate public interfaces; they do not repair candidate code. [Reproduction guide](reproduction.md), [benchmark infrastructure](benchmark-infrastructure.md), [evidence manifest](results/evidence-manifest.json).

Local `pnpm check-all` passed, including 571 tests across 14 files, and fresh package installation succeeded. These counts support reproducibility; ratings depend on the boundaries and failure properties actually tested. Each external review records its own build/test results and publication discrepancies. Platform-dependent candidates retain explicit untested gates when this environment cannot execute their actual entry.

The fixture itself required calibration: an initially invalid PNG, image recompression, timeout observation margins, and generic response parsing all needed adjudication. Obsolete runs are retained and marked; final claims use current source hashes and the [independent review](independent-review.md). A raw pass count is deliberately **not** the ranking input: a code-mode tool can return success after a lost mutation, and an always-disconnected tool can return promptly without exercising the injected fault. [Validation notes](validation-notes.md).

This is not full OBS/MCP conformance testing. The fake covers selected requests and state transitions, not all 147 request schemas, event-confirmed workflows, or batch semantics. A pre-apply disconnect of an idempotent scene setter does not establish safety after an uncertain non-idempotent mutation. No claims are made about real rendering, codecs, capture devices, live streaming, OS startup, all MCP transports, or production performance. Architecture scores remain evidence-backed judgments; source-only findings have lower runtime confidence.

The [chronological research index](../obs-research-index.md) preserves earlier work. This study supersedes its source-only conclusions where stronger execution or field evidence changes the answer; historical reports remain unchanged.

## Architecture and state model

The implementation separates configuration, OBS transport/auth/correlation, request descriptors, domain operations and schemas, MCP tool registration, resources, and HTTP/stdio lifecycle. Tools depend on a passed `ToolContext` containing the client/config rather than a process-global OBS singleton. Effect Schema supplies input validation, JSON Schema, and output validation; the client handles pending requests and timeouts, while the reconnecting wrapper owns backoff and event-listener continuity. [Tool mechanics](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/src/mcp/tools/mechanics.ts), [client](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/src/obs/client.ts), [reconnecting client](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/src/obs/reconnecting-client.ts).

MCP responses contain JSON text plus structured content on success; execution errors use `isError: true` and structured `_meta`. Registration is filtered by toolsets and OBS's advertised request set. Resources include static and templated read views with event/tool invalidation, plus stateful HTTP subscriptions; stateless HTTP disables subscriptions. No MCP prompt or completion handlers are registered. [MCP server](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/src/mcp/create-mcp-server.ts), [runtime setup](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/src/mcp/server.ts), [resource catalogue](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/src/mcp/resources/index.ts).

### Field fidelity: more specific than the prior update scan

A reproducible [top-level field audit](../audit-local-fields.mjs) compares all official requests with exported runtime descriptor schemas and records associated public tool schemas. Its [output](../results/local-field-audit.json) is a discovery aid, not a nested-schema or forwarding proof. Manual source review confirms three locator omissions:

1. `GetSceneList` / `list_scenes` cannot receive `canvasUuid`.
2. `CreateInput` / `create_input` cannot receive `canvasUuid` with a scene-name locator.
3. `SetCurrentProgramScene` / `set_current_scene` cannot receive `sceneUuid`. The schema-limited batch setter is name-only too, so it is not a workaround.

The first two were found in the earlier audit; the third is additional evidence from this study. [Scene descriptors](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/src/obs/requests/scenes.ts), [input schemas](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/src/domain/schemas/inputs.ts), [batch schemas](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/src/domain/schemas/batch.ts).

**Observed through the freshly installed MCP artifact:** all three locator arguments are rejected before any OBS request is sent. Nested input settings survive reads; filter reads retain only name/type metadata; the output read drops the fixture's nested encoder settings; current transition reads omit settings; nested filter/output/transition writes return tool errors before dispatch. The [targeted runtime evidence](../results/local-fields-runtime.json) and [reproduction script](../probe-local-fields.mjs) corroborate these static findings. Rejected fields are limitations, not falsely successful writes. An initial filter invocation used the wrong fixture filter name; the final run uses the existing `Synthetic Color` entity.

The earlier shorthand “147 descriptors” is imprecise: `OBS_REQUEST_TYPES` declares 147 request names, while there are 146 exported request-descriptor objects and batch-only handling for `Sleep`. The built-in parity audit parses the name list and required-request annotations; it does not inspect descriptor bodies or field fidelity. This is not a missing standalone Sleep feature, because the official protocol makes Sleep batch-only. [Parity script](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/scripts/audit-protocol-parity.ts), [official protocol evidence](../results/official-protocol.json).

Other deliberate limits carry real user costs:

- Filter reads reduce values to sorted name/type summaries; writes translate nine allowlisted controls. Crop/compressor/plugin settings therefore cannot be expressed through the general filter tool. [Filter operations](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/src/obs/operations/filters.ts).
- Generic output settings retain nine typed fields. [Output schemas](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/src/domain/schemas/outputs.ts).
- The current transition response decoder accepts settings but the public operation omits them; mutation accepts flat primitive values. [Transition operations](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/src/obs/operations/transitions.ts).
- Screenshot reads return the whole bounded base64 payload with MIME/byte metadata; the allowed format list is static. Saves enforce a configured existing directory and simple filename. The directory is checked in the MCP host filesystem while OBS performs the save, which assumes compatible path visibility for remote OBS deployments. [Screenshot operations](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/src/obs/operations/screenshots.ts).
- The MCP success wrapper emits screenshot bytes inside JSON text/structured content, not as native `type: image` content. The bytes can be decoded by a client, but immediate visual model consumption is a separate usability question; complete base64 does not by itself establish the best visual workflow. [Success wrapper](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/src/mcp/create-mcp-server.ts).
- Setting every toolset to enabled does not create a generic official-request escape hatch: `admin_raw` is persistent data and `vendor` is plugin-defined vendor calls. [Registry](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/src/mcp/tools/index.ts).

## Documentation and scope caveats

The generated README accurately documents many field restrictions, but [`docs/architecture.md`](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/docs/architecture.md) still calls implemented HTTP, screenshots, batches, and studio-mode writes deferred. The README's statement that context is returned “without connecting” describes the operation, while ordinary server startup establishes an OBS connection before MCP initialization; discovery mode is a separate synthetic-capability mode. These are documentation/entry distinctions, not proof that a disconnected ordinary session works. [Runtime](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/src/mcp/server.ts).

The prior discovery report mentioned tool annotations, but current `tools/list` emits name/title/description/inputSchema/outputSchema without behavior annotations. Documentation and schema strictness should not be described as implemented `readOnlyHint`/`destructiveHint` annotations. [Listing handler](https://github.com/dearlordylord/obs-mcp/blob/587e356b00d9269dcd124969ee36aad9635f2db8/src/mcp/create-mcp-server.ts).

No real OBS/codec/device/rendering checks are asserted by this research. Existing integration tests are opt-in and were not enabled.

## Runtime boundary and gates

This is not a conventional stdio server over ordinary OBS requests. The sidecar first verifies the exact OBS PID, authenticates to OBS WebSocket, and sends `CallVendorRequest` to an in-process `dcc-mcp-obs` plugin; MCP is then exposed on a separate DCC-MCP network endpoint. In the final shared fixture, the published wheel authenticated and emitted `CallVendorRequest` with `vendorName=dcc-mcp-obs` and typed request `GetPluginStatus`. The fixture correctly classified the unavailable candidate-specific vendor implementation as `fixture_unimplemented`; the sidecar failed closed with `OBS_REQUEST_FAILED` before MCP startup. The raw runner's initialization `fail` is therefore manually classified **NT**, not an implementation failure.

## Changeability traces

- **One OBS request:** add a native vendor registration and handler in `plugin-main.cpp`; add the request name to `VENDOR_REQUESTS` and mutation classification where needed; add a typed bridge method; expose a bounded YAML tool/script; update the capability matrix and native/protocol/bridge/MCP tests. No generic dispatch path can silently bypass review.
- **One nested settings kind:** extend the reviewed-kind allowlist and bounded native property conversion, bridge validation/readback, YAML nested schema, skill wrapper, round-trip and rollback tests. Arbitrary settings remain deliberately unavailable.
- **An event-confirmed workflow:** native frontend callbacks already advance event sequence and identity travels on each response. Add the specific event/readback contract, bounded bridge reconciliation under the inherited deadline, tool workflow, and disconnect/overflow/late-event tests.
- **A second MCP transport:** DCC core owns the independent control endpoint and Gateway integration, while OBS transport stays below `ObsControlBridge`. Add transport configuration/composition in server/runtime packaging and session-lifecycle tests; native request implementations remain unchanged.
- **Canvas identity:** introduce canvas UUID/version fields in native identity and affected response/request types, pin them in `_Identity`, propagate them through bridge postconditions and YAML schemas, then add drift/recreation tests. The existing PID/instance discipline is a useful model.

## Independent lessons

Worth adopting: exact process plus instance identity on every response; stable event sequence; one absolute deadline propagated across layers; post-send mutation uncertainty; explicit readback after acceptance; stable public error allowlists; bounded frame/event handling; versioned capability matrices; typed settings allowlists; and packaging provenance tied to release workflow and commit. Avoid: keeping material unreleased source changes under the published version number and requiring a platform-specific core executable without an aarch64 fallback or source artifact.

## Parent

[Establish OBS adoption contracts, current baseline, and maintained acceptance fixture](https://github.com/dearlordylord/obs-mcp/issues/8)

## What to build

An operator can distinguish shipped behavior from planned changes and find the exact compatibility rules for settings and screenshots.

## Acceptance criteria

- [ ] Record the source commit, lockfile identity, package version and current quality-gate results; retain historical study evidence unchanged.
- [ ] Document exact names, opt-in/toolset boundaries, bounded recursive JSON limits, sensitive-field exclusions and each settings write's merge/replacement contract before feature implementation.
- [ ] Record native-image result compatibility, existing metadata compatibility, retention ownership and supported screenshot save topologies before feature implementation.
- [ ] Correct current transport/control/startup documentation and distinguish normal defaults from discovery configuration; link deferred findings to their existing destinations.
- [ ] Retain TypeScript/Effect, schema-first descriptors, static registration and existing registry/quality gates; document pending gaps without describing them as fixed.
- [ ] Record which existing resources can express the added locators; preserve unscoped resource contracts and explicitly explain inapplicable mappings rather than invent new resource APIs.
- [ ] Record the supported Node runtime contract consistently with package metadata, documentation and the existing Node 22/24/26 acceptance matrix; identify any current mismatch explicitly.
